# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev        # Start dev server (Vite frontend + Express backend together)
npm run build      # Build client (Vite) + bundle server (esbuild → ESM)
npm run start      # Run production build
npm run check      # TypeScript type checking (no emit)
npm run db:push    # Push Drizzle schema changes to the database
npm run seed       # Seed the database with initial data
```

There is no test framework (no vitest/jest/playwright) — but this is not "no automated tests":
`npm run test:pure` runs a growing set of hand-rolled, DB-free `scripts/verify-*.ts` scripts (plain
`tsx` programs, `PASS`/`FAIL` per assertion, nonzero exit on failure) that lock in the security/money
invariants below, and it runs on every push/PR via CI (see "CI" under Security & data-integrity
invariants). Several more `scripts/verify-*.ts` exist but touch a live DB and stay manual-only.

## Architecture

This is a monorepo restaurant POS system. All dependencies live in the root `package.json`. The three main layers are:

### `shared/`
- `schema.ts` — Single source of truth for all database tables (Drizzle ORM + Zod). Core tables: `users`, `categories`, `menuItems`, `inventory`, `orders`, `orderItems`, `kotTickets`, `tables`, `sales`. TypeScript types are inferred directly from the schema and shared between client and server via the `@shared/*` path alias.

### `server/`
- `index.ts` — Express app setup: sessions (MemoryStore, 24h), Passport, body parsing, Vite dev integration.
- `routes.ts` — All API endpoints (~47KB). Includes: Passport-local auth strategy, WebSocket server (order + KOT real-time updates), and all REST handlers. Auth middleware: `requireAuth` (session), `requireAdmin` (role check).
- `storage.ts` — `IStorage` interface + `DatabaseStorage` implementation. All DB access goes through this abstraction (repository pattern). Drizzle queries live here, not in routes.
- `settingsStore.ts` — Restaurant settings persisted to `restaurant-settings.json` (not DB). Includes `posRoleTimeout` (minutes before elevated POS role auto-reverts).
- `db.ts` — Neon serverless PostgreSQL connection via `DATABASE_URL` env var.
- `dataDir.ts` — `dataDir()`/`dataPath(name)` resolve the writable base for server-managed files (`restaurant-settings.json`, `automation-config.json`, `baileys-auth/`, …). Returns `process.env.BAGICHA_DATA_DIR || process.cwd()`. **Any new cwd-relative file write must go through `dataPath()`**, or it breaks in the packaged Electron host build (read-only cwd). `settingsStore.ts`, `automationStore.ts`, `baileysDriver.ts` use it.
- `whatsappRoutes.ts` — WhatsApp driver control, agent-inbox endpoints (`/api/whatsapp/*`), and the public Meta webhook.
- `services/whatsapp/` — WhatsApp automation subsystem (see "WhatsApp Automation" below).
- `printRoutes.ts` / `printService.ts` — KOT/bill printing endpoints (see "Printing (KOT/Bill)" below).

### `client/src/`
- `App.tsx` — Wouter router with auth guard. POS is full-screen (no TopNav). All other pages use TopNav + sidebar layout.
- `pages/` — One file per route. `POS.tsx` is the most complex page (order management, role switching, PIN gates).
- **Live tables** (`pages/LiveTablesDashboard.tsx` + `components/live-tables/OrderCard.tsx`): dine-in cards source data from `useLiveTableOperations.ts` (fetches `/api/tables` + full `/api/orders/:id` per running table; WS `NEW_ORDER`/`ORDER_UPDATE` diff). "Assigned staff" = `orders.createdByName` (set at order create, exposed by `getTables()` as `servedByName`, same value the "Staff on Floor" panel in `Tables.tsx` uses); the card also shows `customerName`. There is no separate table→waiter assignment field. **Never re-set `createdByName` outside order creation** — `PUT /api/orders/:id/items` used to stamp it to the *current* actor on every item edit, so a long-running table edited the next day by a different logged-in user would silently flip "served by" to them (fixed; see [routes.ts](server/routes.ts) `items` route).
- `components/ui/` — shadcn/ui components (do not edit these manually).
- **Horizontal-scroll tab rows** (e.g. Customers page tabs in `CustomerDashboard.tsx`): use `shrink-0 sm:flex-1` on the buttons, never `flex-1 min-w-0` — `min-w-0` lets nowrap labels collapse below content width and visually overlap on mobile instead of scrolling.
- `hooks/` — Custom hooks:
  - `useAuth` — Auth session state via React Query (`/api/auth/me`)
  - `useRole` — Reads login role from auth session (`admin | manager | staff`)
  - `useActiveRole` — POS role switcher state with countdown timer; elevating above login role starts auto-revert
  - `usePermission(activeRole)` — Returns `can(action)`, `requirePin(label, fn)`, `isLocked()` for role-gated POS actions
  - `useManagerAuth` — PIN popup state machine (60s unlock window after correct PIN)
- `lib/queryClient.ts` — TanStack Query client + `apiRequest` helper (wraps fetch with session cookies).

## Role / PIN System

Three POS roles: `admin > manager > staff` (defined in `useRole.ts` as `ROLE_LEVEL`).

- **Admin** — full access, no PIN ever required.
- **Manager** — restricted actions need admin PIN.
- **Staff** — most restricted; saving an order requires manager PIN; restricted actions need manager PIN.

Restricted actions (admin-only without PIN override): `discount`, `complimentary`, `clearCart`, `newOrder`, `cancelOrder`, `moveTable`, `mergeTable`, `splitBill`.

PIN verification endpoint: `POST /api/auth/verify-pin` accepts `{ pin, requiredRole }`. `requiredRole="admin"` only accepts admin PINs; `requiredRole="manager"` accepts manager or admin PINs.

The `RoleSwitcher` component in the POS top bar lets any logged-in user temporarily elevate their role via PIN. Switching to a higher role than the current **active** role (not login role) triggers a PIN prompt.

## Security & data-integrity invariants (server-enforced — do not regress)

Client-side PIN gates are UX only; the server enforces the following independently. Full rationale in `SECURITY-REMEDIATION.md` (owner steps) and the audit plan.

- **Privileged-action elevation** (`server/elevation.ts`, pure + unit-tested via `scripts/verify-elevation.ts`): `POST /api/auth/verify-pin` stamps a 90s session grant (`grantElevation`); privileged endpoints call `requireElevation("manager")` / check `hasElevation`. Gated: `/orders/:id/cancel`, `/move-table`, `merge`, `/split`, `POST /api/tables/:id/shift` (same effect as `/move-table` — relocates an active order to another table, gated the same way both server-side and client-side via `usePermission`'s `go("moveTable", …)` + `PinGuard` in `Tables.tsx`), and **applying a discount** on `POST /api/orders` + `PUT /api/orders/:id/items`. A bare staff session (or curl) can't hit these. Re-exported from `routes.ts` for back-compat.
- **Server recomputes all money** (`shared/orderPricing.ts` pure core + `server/services/orderPricing.ts` DB wrapper; `scripts/verify-order-pricing.ts`). Never trust client totals. `priceOrder` validates each line's client price against a DB **floor** (matched size price, else base `menuItems.price`; add-ons/variants only add), then recomputes subtotal/tax/discount(clamped to `[0,subtotal]`)/container/total using `getSettings().taxRate`. `POST /api/orders` + `PUT /items` store the recomputed values + validated unit prices. Merge/split use `computeTotalsFromLines` (configured tax, **and now a container-charge term** — see below) — **no more hardcoded `0.18`**.
- **Merge/split are atomic and copy the full item row.** `storage.mergeOrders`/`storage.splitOrder` (`storage.ts`) wrap the item copy + totals recompute + table-free/order-delete (merge) or new-order-create + item-move (split) in one `db.transaction` — previously these were unwrapped sequential statements, so a failure partway through could duplicate items across two orders or delete a source order while its items still existed. Both now copy `name`/`serviceMode`/`parcelLeftover`/`unitCost` in addition to `menuItemId`/`quantity`/`price`/`specialInstructions`/`size` — dropping those broke open items (no stored name), lost the container-charge basis, and blanked the COGS snapshot. `shared/orderPricing.ts`'s `computeContainerCharge(items, containerRate)` is the single source of truth for the ceil-per-line container rule (factored out of `priceResolved`, reused by merge/split) — both routes now persist a real `containerCharge`/`subtotalAmount` on the affected orders instead of silently dropping the charge. Split's existing discount is left entirely on the source order (aggregate-neutral by design — verified: `(S1-0)+(S2-D) = S-D`, same total tax owed as before the split) UNLESS it now exceeds what remains after the split-out items leave, in which case the route refuses with a 400 instead of letting `computeTotals`' clamp silently lose the excess (a real net overcharge across the two resulting bills — this was the actual bug, not "discount duplication"). Regression-locked by `scripts/verify-merge-split.ts` (in `test:pure`) — pure math only; the transactional wiring itself needs a live DB to exercise.
- **Server owns all payment state, not just totals.** `PUT /api/orders/:id` used to accept `insertOrderSchema.partial()` — every column, including `totalAmount`/`paymentStatus`/`paidAmount`/`changeAmount` — behind only `requireAuth`, so any logged-in session (bare staff PIN included) could rewrite a total or mark an order paid with zero recompute and zero elevation check. It's now `shared/orderMutation.ts`'s `orderUpdateAllowlist` — `status`/`notes`/`customerName`/`customerPhone` only; everything else is silently stripped by Zod's default strip-unknown-keys behavior, not just "unvalidated". The only confirmed client caller (`Orders.tsx`) sends `{status}` alone; add fields to the allowlist deliberately, never widen it back to the full schema. `POST /api/orders` also force-sets `paymentStatus:"pending"`/`paidAmount:null`/`changeAmount:"0"`/`paymentMethod:null`/`paymentBreakdown:null` (`ORDER_CREATE_FORCED_DEFAULTS`, spread last so it always wins over the client body) — an order could previously be created already `paymentStatus:"paid"` by simply including that field in the request. Regression-locked by `scripts/verify-order-mutation-guard.ts` (in `test:pure`).
- **`orders.subtotalAmount` + `orders.containerCharge` are now persisted, not reconstructed.** `orders` used to store only `totalAmount`/`taxAmount`/`discountAmount`, so every reader that needed a "subtotal" derived it as `totalAmount - taxAmount` — correct ONLY when discount = 0 AND containerCharge = 0 (the true relation is `total = (subtotal - discount) * (1 + taxRate) + containerCharge`, per `priceResolved`). With a real discount and a real container charge, that reconstruction was off by a very real amount — the printed bill's "Sub Total" line didn't match the actual item sum, the container charge was invisible on the bill, and applying a coupon/loyalty discount on top used the wrong base and dropped the container charge from the recomputed total entirely. Fixed by snapshotting both at order-creation/edit time (`POST /api/orders`, `PUT /api/orders/:id/items`) from the same `priced` object that already computes the other three columns, and adding `shared/orderPricing.ts`'s `deriveBillTotals(order)` — prefers the persisted columns, falls back to `total - tax` only for legacy rows written before the columns existed (not retroactively recomputed). **Every reader of "subtotal" must go through `deriveBillTotals`, never re-derive it as `total - tax` directly** — that was the bug. Both bill renderers (`server/printRoutes.ts`'s `billTextLines`, `shared/print/generators.ts`'s `generateBillBuffer` — CLAUDE.md's "Printing" section on keeping these two in sync applies here too) print a "Container" line when nonzero. `POST /api/coupons/apply` + `POST /api/loyalty/redeem` (`growthRoutes.ts`) now go through `deriveBillTotals` + the configured tax rate (`pricingRates()`, not a hardcoded `0.18`) and preserve the container charge in their recomputed total; both are now `requireElevation("manager")` (they apply a discount, same as every other discount path). Regression-locked by `scripts/verify-bill-derivation.ts` (in `test:pure`, includes the exact worked counterexample from the audit that found this). **⚠️ Migration required**: `scripts/migrate-order-subtotal.mjs` adds the two columns (additive-only, nullable/defaulted) — this has **not been run** against the shared DB as part of this change; until it is, every `POST /api/orders`/`PUT /api/orders/:id/items` will fail with a Postgres "column does not exist" error, since Drizzle now generates SQL referencing both columns. Run it before deploying this change.
- **Payment** (`POST /api/orders/:id/payment`): paid amount is derived from the entered breakdown (not client `totalPaid`), change is recomputed server-side, and a non-due settle must cover the bill (₹1 tolerance). Settlement is guarded by `storage.settleOrderIfUnpaid` (conditional `WHERE paymentStatus='pending'`) so a concurrent double-settle is a no-op and loyalty/message/feedback fire **once**. `storage.settleCustomerTabs` (bulk "pay the whole week" settle, see the Pay Later section below) now uses the same conditional guard on its UPDATE — it used to compute the matching order ids from an earlier SELECT and write to exactly those ids with no re-check, so a single-order settle landing in between could get silently overwritten; it also now returns the count of rows the UPDATE actually flipped (via `.returning()`) rather than the stale pre-computed count.
- **Atomic order creation**: `storage.createOrderWithItems` wraps order + items + KOT in one `db.transaction` (the only transactional path; inventory/table status stay best-effort outside).
- **Bill/KOT counters** (`settingsStore.ts`): `incrementBillCounter`/`incrementKotCounter` allocate the next number via a single atomic `UPDATE restaurant_settings ... RETURNING`, not the in-memory `settingsCache`. A per-process promise-chain mutex (the previous approach) only serializes issuance *within one Node process* — on Vercel every serverless instance holds its own cache and mutex, so two instances handed out the same `orderNumber`/`kotNumber`; the loser hit the UNIQUE constraint and the generic catch in `POST /api/orders` reported it as `400 "Invalid order data"`, which cleared on retry once the instance caught up. The atomic `UPDATE` takes a row lock on `restaurant_settings.id=1`, so every process — desktop host or any Vercel instance — reads-and-increments through Postgres itself; concurrent callers queue instead of colliding. Verified by `scripts/verify-counter-race.ts` (DB-touching, run manually — proves the old per-instance-cache approach collides under concurrency and the atomic one doesn't). `POST /api/orders`'s catch block now only returns 400 for a genuine `priceOrder` rejection (bad item/qty); every other failure (DB, counters) is a 500 — don't reintroduce a blanket "any exception → 400" here, it's what hid this bug.
- **`saveSettings()` no longer rolls the bill/KOT counter backward.** It used to read the current row (`readSettingsFromDb`), merge in JS, then write the WHOLE merged blob back as two separate round trips with no lock between them — if `issueCounter`'s atomic `jsonb_set` UPDATE (above) landed and committed in that window, `saveSettings`' write still had the stale counter value it read earlier baked into `updated`, and stomped the just-incremented counter back down. Fixed: the read, merge, and write now happen inside one `db.transaction`, with `SELECT ... FOR UPDATE` on `restaurant_settings.id=1` taken first — a bare `UPDATE` on a locked row (which is exactly what `issueCounter` does) blocks until this transaction commits, so a counter increment can no longer land inside the window. Any future change to `saveSettings`' merge logic must stay inside that same transaction/lock, not read outside it.
- **`reconcileOrderInventory` (`storage.ts`) is now safe against two concurrent edits of the same order.** It diffs a fresh target against `stock_movements`' "already applied" aggregate and applies only the difference (see the function's own doc comment for why) — that read used to happen *outside* any lock, so two concurrent `PUT /api/orders/:id/items` calls for the same order could both read the same baseline and both apply the full diff, double-deducting stock. `pg_advisory_xact_lock(orderId)`, taken first inside the transaction that now wraps both the read and the diff-apply, serializes concurrent calls for *that specific order* (other orders' reconciliation proceeds unblocked) and releases automatically on commit/rollback. Plain READ COMMITTED alone does not prevent this class of race — it only guards visibility within one statement/transaction, not a read in one transaction followed by a write in a later, separate one.
- **`PUT /api/orders/:id/items` is now transactional.** `storage.replaceOrderItems(orderId, items, totals)` wraps the delete-all-then-reinsert plus the totals update in one `db.transaction` — previously these were three unwrapped statements, so a crash/error between the delete and the reinsert left the order with zero items and no way to recover short of a manual DB fix.
- **Print counters (`kotPrintCount`/`billPrintCount` in `printRoutes.ts`) are incremented atomically in SQL** (`sql\`${orders.kotPrintCount} + 1\``), not as `(order.kotPrintCount ?? 0) + 1` computed from a value read earlier in the same request handler — the latter is a classic lost-update: two concurrent prints of the same order could both read count=3 and both write count=4, silently losing one increment.
- **Auth gates**: `/api/automation/config` GET+POST are `requireAdmin` (mask now also hides `metaAppSecret` + `metaWebhookVerifyToken`); `/api/staff` + `/api/staff/performance` are `requireManagerOrAdmin` (salary/biometric) — `GET /api/staff` is registered once, in `staffRoutes.ts`, since `routes.ts` used to carry a second, weaker (`requireAuth`) registration of the same path that was dead code only because of registration order (removed, don't re-add it); `PUT /api/staff/:id/profile` (writes `monthlySalary`/`biometricId`) is `requireManagerOrAdmin` too, matching the read gate. `POST /api/automation/run` is `requireAdmin` (matches `/api/automation/config`'s gate) — it force-triggers a **real outbound WhatsApp send batch** (`runCustomerAutomation({force:true})`, bypassing the `config.enabled` check), not a dry-run, so a bare staff session running it was a genuine ban-risk surface per the send-volume warning above. `DELETE /api/automation/logs` is `requireAdmin` too (unconditional wipe, no confirmation). `POST /api/crm/customers/:key/message` (send an outbound message to a customer) is `requireManagerOrAdmin` — no client caller currently exists for it, so this closes a reachable-but-unused hole with zero UI regression risk.
- **Realtime is authenticated**: the `/ws` upgrade is checked against the session cookie (sessionMiddleware threaded into `registerRoutes` from both `server/index.ts` and `server-fn.ts`); Pusher uses a **private channel** (`private-bagicha-pos` default) authorized by `POST /api/pusher/auth` (`requireAuth`) — client `useRealtime.ts` wires a `channelAuthorization.customHandler`. Server `PUSHER_CHANNEL` and client `VITE_PUSHER_CHANNEL` must match.
- **Delivery webhook** (`POST /api/delivery/webhook/:platform`): now fail-closed — requires `x-webhook-secret` == `DELIVERY_WEBHOOK_SECRET` and a known platform.
- **Loyalty/coupon redemption is lock-protected against concurrent double-spend.** `loyaltyService.redeemPoints` used to `getBalance()` (a `SUM` over the append-only ledger — no mutable balance column to row-lock), compare, then insert a negative row with no lock spanning the two — two concurrent redemptions (double-tap, retried request) could both read the same balance, both pass, and both insert, driving the balance negative and double-applying the discount. `couponService.redeemCoupon` had the same shape: its usage-limit/per-customer-limit counts (via `validateCoupon`) and the redemption insert were unlocked, so a single-use coupon (`usageLimit:1`, e.g. auto-issued birthday/NPS-recovery coupons) could be redeemed twice by two near-simultaneous requests. Both now wrap the count-recheck + insert in one `db.transaction` with `pg_advisory_xact_lock` — keyed on a hash of `customerId` for loyalty, on `couponId` for coupons — serializing concurrent redemptions for that specific customer/coupon without blocking unrelated ones.
- **Hardening**: `helmet()` on both entries; session cookie `secure` in prod + `sameSite:"lax"`; `SESSION_SECRET` **required in production** (`server/sessionSecret.ts` throws on boot if unset — no more hardcoded fallback; `.session-secret` file deleted). Multer capped at 5MB + spreadsheet/CSV `fileFilter` before `XLSX.read`. Config file writes (`automationStore.writeJson`) are atomic (temp+rename). `process.on('unhandledRejection'|'uncaughtException')` guards in `server/index.ts`.
- **Observability**: `client/src/components/ErrorBoundary.tsx` wraps the whole render tree in `main.tsx` (there was no ErrorBoundary anywhere before — a single render-phase throw white-screened the app with no fallback and no report). `main.tsx` also adds `window.onerror`/`unhandledrejection` listeners for errors outside React's render cycle (event handlers, timers, promise rejections), which an ErrorBoundary can't catch. `client/src/lib/queryClient.ts`'s `QueryClient` now has a `queryCache.onError` (console.error + `Sentry.captureException`, no toast — most queries poll every 5s and a toast per failed poll would spam) and a `mutationCache.onError` that shows a fallback toast **only** when the specific mutation has no local `onError` (checked via `mutation.options.onError`) — closes several previously-silent mutations (`useConversations.ts`'s reply/takeover/returnToBot/markRead, `Menu.tsx`'s delete, `Staff.tsx`'s remove) without double-toasting the ~45 mutations that already handle their own error. `GET /api/health` + `GET /api/version` (both unauthenticated, `routes.ts`) — no liveness/diagnostic probe existed before. `vite.config.ts` and both `esbuild` build commands (`build`, `build:api`) now emit source maps — without them a production/Sentry stack trace only pointed at minified bundle offsets. `server/index.ts`'s global error middleware now always `console.error`s (previously only reported to Sentry when `SENTRY_DSN` was set, so a 500 with no DSN configured was invisible in any log); the request logger's truncation is 500 chars for non-2xx responses (was a blanket 80, which cut off the one thing that showed what failed). `SENTRY_DSN`/`VITE_SENTRY_DSN` are installed and initialized (`server/index.ts`, `client/src/main.tsx`, and now `server-fn.ts` too — it previously had no `Sentry.init`/`process.on` guards at all, so the Vercel path got zero error tracking even with a DSN set) but were undocumented in `.env.example` — now listed there; Sentry stays a no-op until a real DSN is set in the deployment's environment.
- **CI** (`.github/workflows/ci.yml`): `npm run check` + `npm run test:pure` on every push/PR. `test:pure` runs the two DB-free verify scripts; the DB/settings-touching `verify-*.ts` stay manual.
- **PINs are still plaintext** (known residual, not in this pass) — hashing them is a tracked follow-up.

## WhatsApp Automation

`server/services/whatsapp/` implements automated outbound sending, an inbound FAQ chatbot, and the agent inbox (Customers → Conversations tab):

- **Driver layer** — `types.ts` defines the `WhatsAppDriver` interface; `baileysDriver.ts` (unofficial, QR-paired via `@whiskeysockets/baileys`, version pinned **exactly** — never add a caret; all Baileys imports stay in this one file) and `metaDriver.ts` (official Cloud API, inbound fed by the webhook). `driverManager.ts` owns the singleton; **only `server/index.ts` may init it** (never a serverless entry). Active driver chosen by `whatsappDriver` in `automation-config.json` (`baileys | meta | none`).
- **Outbound** — `outboundQueue.ts` drains the `automation_jobs` table through the driver with `sendDelayMs` + jitter pacing, retries, and a `maxPerDay` cap. `customerAutomationService` enqueues when `whatsappAutoSend=true` (off = legacy manual wa.me flow). `messagingService` sends driver-first for the whatsapp channel. Opt-out is re-checked at send time.
- **Inbound** — `inboundService.ts` upserts `conversations` (per-phone threads; `customerId` is a best-effort last-10-digit match into `customers_master`), persists to `conversation_messages`, and runs `botService.ts` (pure keyword FAQ matcher — answers from `settingsStore` + config; STOP opts out via a *targeted* `doNotSendUpdate` update — never `upsertCustomerProfile`, which nulls the whole profile row). Human takeover silences the bot; it returns after `botReturnMinutes` idle. `detectIntent` uses whole-word regex with an **optional trailing `s` for keywords ≥4 chars** so plurals match ("hour"→"hours") while short words stay strict ("hi"≠"his").
- **Delivery tracking** — `deliveryService.ts` applies receipts to both `conversation_messages` and `customer_messages` by shared `waMessageId`, with a status-rank guard (pending<sent<delivered<read; failed terminal).
- **Realtime** — services publish `WA_MESSAGE | WA_STATUS | WA_CONVERSATION_UPDATE | WA_CONNECTION` via `publishRealtime()`. Client: `useConversations.ts` + `components/conversations/`. Local WS now connects in production LAN builds too (Pusher-only when `VITE_PUSHER_KEY` is set).
- **Footguns** — Baileys session lives in `baileys-auth/` (gitignored; wiped automatically on loggedOut). Ban avoidance: keep `sendDelayMs ≥ 3000`, low `maxPerDay`, warm up fresh numbers. **Benign log noise (not bugs):** `Bad MAC` / "Failed to decrypt message with any known session" come from `libsignal` trying to decrypt WhatsApp **Status updates** (`status@broadcast`) and messages from stale pre-restart sessions — undecryptable and irrelevant; can't be silenced without patching `node_modules`. `baileysDriver.ts` skips non-`@s.whatsapp.net` JIDs (groups/broadcasts/newsletters) silently.

### Settlement-time messaging

Customer-facing messages fire at **bill settlement** (`POST /api/orders/:id/payment`), **not** at order-save. Order-save (`POST /api/orders`) only records the visit (`logOrderPlaced` + segmentation) — no message. Dispatchers live in `automationRuleEngine.ts`:
- `triggerSettlementMessage(key,name,phone)` — paid branch. New customer (`totalVisits ≤ 1`) → WELCOME (gated by `settlementWelcomeEnabled`); returning → per `settlementReturningMode` (`off | auto | vip_reward | favorite_item | thank_you`). `auto` = VIP→VIP_REWARD, Regular+fav→FAVORITE_ITEM, else thank-you (`settlementReturningText`).
- `triggerDueBillMessage(orderId,name,phone)` — `else` (due/unpaid) branch. Sends an itemized reminder built via `buildOrderBillBlock(orderId)` (extracted so the consolidated e-bill below reuses the same logic); `dueMessageTemplate` wraps it with `{name} {restaurant} {due} {bill}` tokens (`{bill}` = item list).
- Both: one message per customer per day (`hasJobToday` guard on `automation_jobs`), then `dispatchSettlement` → `enqueueWhatsApp` when `whatsappAutoSend` + driver, else legacy `sendMessage`. Blank templates fall back to defaults in `automationStore` / `automationRuleEngine`.
- Per-customer snapshot: `buildSnapshotForKey` (exported from `customerAutomationService.ts`). Admin UI: "Checkout messages" card in `AutomationPanel.tsx` SetupTab (5 config fields, persisted via `/api/automation/config`).
- **Ownership split (avoid duplicates):** settlement owns WELCOME / VIP_REWARD / FAVORITE_ITEM / THANK_YOU / due-reminder. The background engines do **lapsed re-engagement only** — `evaluateTrigger` (`customerAutomationService.ts`, hourly) and `evaluateDefaultTriggers` (`automationRuleEngine.ts`, daily) emit only WIN_BACK / AT_RISK / INACTIVITY_*. Do not re-add welcome/VIP/favourite to either engine.
- **Same-day dedup = resolved `customerId` on `automation_jobs`** (never the phone-vs-name `key`). Every send path resolves via `resolveCustomerId` then checks `automation_jobs` for today: settlement `hasJobToday`, daily engine's `recentJob`, and `enqueueWhatsApp` (which also blocks a same-day **sent** job for the same `customerId+trigger`, not just pending/sending).

### "Pay Later" = Mark as Due = a customer's open tab (one concept, not three)

There is **no separate "tab" or "hold" concept for deferred payment** — a customer who "pays later" is simply an order settled with **Mark as Due** checked in `SettlementDialog.tsx` (label reads "Pay Later — add to customer's tab"), which sets `orders.status="served"` + `paymentStatus="pending"` via `POST /api/orders/:id/payment`. This is unrelated to Hold/Recall (`status="hold"`), which parks an *unfulfilled* order (table freed, nothing served, nothing owed) — never conflate the two.

- **`SettlementDialog`** is the one comprehensive dialog for this — it now optionally renders an order-summary block (customer name/phone, itemized list, subtotal/discount/tax/total) when the caller passes `items`/`subtotal`/`taxAmount`/`discountAmount`/`orderLabel`, and prefills `customerName`/`customerPhone` via `initialCustomerName`/`initialCustomerPhone`. POS passes all of these from `cartItems`/`grandTotal`/the order form. Don't build a second "pay later" dialog — extend this one.
- **Opening it:** the Settle button, **and** a long-press (or right-click) on the order number now shown in the POS cart header (`serialNum(activeOrderId)`, via the inline `longPressHandlers()` helper in `POS.tsx`) both open this same dialog.
- **Per-customer aggregation:** `storage.getOpenTabsByCustomer()` groups all `paymentStatus="pending" && status="served"` orders by `customerPhone || customerName` (not date-bound — outstanding is always "current"). Items resolve via `leftJoin(menuItems)` + `coalesce(orderItems.name, menuItems.name, 'Item')` — **prefer `orderItems.name` first**, then the menu name, then the literal fallback (this file previously described the pattern as just `coalesce(name, 'Item')` — i.e. menu name only — which is what `getOpenTabsByCustomer` actually did until it was fixed: every open item's `orderItems.name` was silently ignored, so it rendered as the literal string "Item" on every Pay-Later tab and consolidated e-bill. Keep the `orderItems.name`-first order for any future order-item query, matching the Open Items section's rule below). `storage.settleCustomerTabs(key)` marks all of a customer's tabs paid at once (the "customer pays the whole week at once" flow).
- **Consolidated e-bill:** `sendConsolidatedEbill({name,phone,orderIds,totalDue})` (`automationRuleEngine.ts`) joins each order's `buildOrderBillBlock` into one message with a grand "*Total outstanding: ₹N*", dispatched via the same `dispatchSettlement` path (driver-auto). `POST /api/dues/send-ebill` also returns a `wa.me` fallback URL for when no driver is connected. This is a separate, owner-triggered action from Reports → **Dues / Pay-Later** — it does **not** replace or dedupe against the automatic per-order `triggerDueBillMessage` reminder.
- Routes: `GET /api/reports/tabs`, `POST /api/dues/send-ebill`, `POST /api/dues/settle-customer`.

### Customer identity

`resolveCustomerId(key,name,phone)` (`customerIdService.ts`) matches by `key` first, then **falls back to last-10-digit phone match** before inserting — prevents duplicate `customers_master` rows when a person was created by name then later referenced by phone (or vice-versa). The CSV import route applies the same phone dedup. `key` = `phone || name`.

## Printing (KOT/Bill)

**⚠️ Never commit compiled `.js` twins next to `shared/print/*.ts` sources.** This bit `desktop/main.ts`'s `import * as E from "../shared/print/escpos.js"` — a real, tracked `escpos.js` sat alongside `escpos.ts` (`generators.js`/`types.js` too), stale by ~2.5 months. esbuild resolves an **explicit `.js`-suffixed** relative import by checking whether that literal file exists *first*, only falling back to resolving against the same-named `.ts` source if it doesn't — confirmed empirically (`esbuild.buildSync` with a stub entrypoint). So the desktop Electron main-process bundle was silently built from the stale compiled file, not current source, for anything imported that way. Separately confirmed the **server bundle was never affected**: `server/printRoutes.ts`/`printService.ts` import via the bare `@shared/print/generators` path alias (no `.js` suffix), and esbuild's *extensionless* resolution tries `.ts` before `.js` — verified by temporarily restoring the stale file and re-resolving that same bare import, which still correctly picked `.ts`. Real-world impact was low (the specific ESC/POS primitives `desktop/main.ts`'s own Test Print calls were unchanged between the stale and current `escpos.ts`) but it was a live landmine: `escpos.ts` had gained `wrapWords`/`DOUBLE_SIZE_ON`/`DOUBLE_SIZE_OFF`/`LOGO_NV_FLASH` since the `.js` twin was generated, invisible to anything reached only through that explicit-`.js` import path. Fixed by deleting the three stale `.js` files — `desktop/main.ts`'s existing `.js`-suffixed imports (its convention throughout the file, matching Node16/NodeNext ESM resolution) now correctly fall through to the `.ts` sources, same as every other import in that file that never had a colliding compiled twin. **Do not regenerate or commit `.js` build output inside `shared/`** — if a build step ever needs one, it belongs in `dist/`, not next to the source.

Two **parallel implementations** render the same KOT/bill text — keep them in sync when changing format:
- `shared/print/generators.ts` (`generateKOTBuffer`/`generateBillBuffer`) — builds the real ESC/POS byte buffer sent to the hardware printer via `/api/print/kot` and `/api/print/bill` (`server/printRoutes.ts`, re-exported through `server/printService.ts`).
- `server/printRoutes.ts` (`kotTextLines`/`billTextLines`) — plain-text lines for the `/api/print/preview` JSON endpoint only.

**Time:** always format via `formatISTDateTime()` (`shared/print/formatDate.ts`, `Intl.DateTimeFormat` pinned to `Asia/Kolkata`) — never read `.getHours()`/`.getDate()` off a raw `Date` for printed output. The server process's ambient timezone is not guaranteed to be IST even though the restaurant is; the client-side HTML bill (`client/src/lib/printBill.ts`) gets this right via the browser's local clock, the server paths didn't until fixed.

**Cashier name:** bill print's `cashierName` prefers `order.createdByName` (who actually created/served the order — same field as the live-tables "served by", see above), falling back to the printing user's username only for legacy orders without it. Don't pass `req.user.username` alone — that's whoever happens to click print, not who served the table.

**Customer name:** when `billSettings.showNameField` is on, print `order.customerName` if present; only fall back to the blank `Name:____` line when no name was captured on the order.

**Header centering (`generateBillBuffer` only):** native ESC/POS `E.ALIGN_CENTER` is active for the whole restaurant-header block — print lines with plain `E.line(str)`, never `E.centered(str, W)` underneath an active `ALIGN_CENTER`. `E.centered` manually left-pads using the *assumed* printer width `W`, and centering that padded string again via the native command double-centers it, drifting away from lines (like the restaurant name) that rely on native centering alone. `generateKOTBuffer` has no `E.centered` calls and isn't affected; `printRoutes.ts`'s plain-text preview uses one consistent manual-centering function throughout (no native commands), so it isn't affected either.

**KOT delta on a quantity increase** (`server/kotDelta.ts` `computeDelta`): when an item's quantity goes *up* since the last print (e.g. 0.5→1), the kitchen only needs to cook the increment — the entry goes into `newItems` with `quantity` = the delta (0.5), not the new total, so the ticket doesn't ask them to redo the whole line. That entry also carries `previousQty` (the old total) so `generateKOTBuffer`/`kotTextLines` can render it unambiguously as `[+0.5]` plus a `now 1 (was 0.5)` sub-line — **never render a bare `[0.5]`** for these, since a genuinely fresh 0.5 order and "0.5 more added to an existing 0.5" would otherwise print identically (this is what happened before the fix: editing 0.5→1 and reprinting looked exactly like the original print, read as a stale-cache bug). Quantity *decreases* are unaffected — they already went through `modifiedItems` with a `was <old>` label before this fix and still do.

**Container charge rounds up per line, never per fractional quantity** (`shared/orderPricing.ts` `priceOrder`, mirrored client-side in `POS.tsx`'s `containerQty`): a container is a physical unit — 0.5 kg of food still needs one whole container — so charge is `Math.ceil(qty) * containerRate` per cart line, summed across lines (ceil-then-sum, not sum-then-ceil: two separate 0.5-qty parcel lines need two containers, not one that a naive `ceil(0.5+0.5)` would give). For a **standalone** (non-table, non-section) pickup/delivery order, every cart item must be sent with `serviceMode` matching the *order type* (`POS.tsx`'s `itemsPayload`, keyed off `isTableSession`) — `activeItemMode` (the per-item toggle used by table/Section POS) never leaves its `"dinein"` default outside those flows, so without this the server's per-item container check (`serviceMode === "pickup"|"delivery"`) sees every line as dine-in and silently drops the container charge from the persisted `orders.totalAmount`, even though the client's own cart total displayed it correctly — this is why the Live Orders rail (which just reads that persisted column verbatim) could show a total ₹15 short of the POS cart's own total for the same order.

**Cart quantity is Edit-only, no inline stepper.** `POS.tsx`'s cart row used to have a −/+ stepper (`updateQty`, now removed) that let any staff member silently change quantity with zero PIN/permission gating — unlike every sibling row action (Edit, Remove, discount, etc.), which all route through `isOff()`/`go()`. Quantity now only displays as plain text in the row; the only way to change it is "Edit Item" (`openEditPicker`/`confirmModal`), which already had its own full quantity input and *is* gated like the other restricted actions.

**Open Items (manual entry, no menu row).** POS.tsx's cart header has an "Open Item" button (gated by the `openItem` restricted action, see Role/PIN section) opening a name+price dialog (`showOpenItemDialog`/`addOpenItem`, `POS.tsx`). Each open item gets a **negative synthetic `menuItemId`** (`openItemSeqRef`, decrementing from `-(Date.now() % 1e9)` per order session — never a real `menuItems.id`) so it round-trips through the existing `CartItem`/payload shape unchanged. `order_items.name` (`shared/schema.ts`) stores the typed name as a snapshot — this column didn't exist before Open Items; every other order-item's name was previously resolved purely by joining `menuItems`, which would have silently dropped rows with no matching menu id. All read paths that used to `innerJoin(menuItems, …)` were changed to `leftJoin` + `coalesce`-style fallback to the stored `order_items.name` (five sites in `server/printRoutes.ts`, plus `dailyDigestService.ts`, `recommendationService.ts`, and — later — `storage.getOpenTabsByCustomer`, whose coalesce had drifted to menu-name-only, and `storage.getCategorySales`, which used `innerJoin(menuItems)`/`innerJoin(categories)` and so dropped open items from category revenue entirely; it now `leftJoin`s both and buckets them under `"Uncategorized"`) — **any new query that resolves an item name (or category) from `order_items` must `leftJoin` menuItems and prefer `orderItems.name`, or open items vanish from that view** (this bit bills/KOT reprints/reports before the fix, and separately bit the Dues report + category revenue). Inventory reconciliation (`reconcileOrderInventory`) already no-ops on an unmatched `menuItemId` (via `getMenuItemById` returning nothing), so open items correctly never touch inventory. `scripts/migrate-open-items.mjs` adds the column via raw ALTER (same pattern as other `scripts/migrate-*.mjs` — see the DB section's warning about `npm run db:push` drift).

**Settlement vs. printing are separate actions, by design.** The intended flow: staff prints the bill first (main "Print Bill" button, before any payment method is chosen) → customer decides how to pay → staff opens the settlement dialog (`SettlementDialog.tsx`), enters the matching amount, and hits "Settle Now". `SettlementDialog` has no print button of its own (removed — it was redundant with this flow and tempted staff into settling before the customer had actually decided). `order.paymentMethod` stays `null` until "Settle Now". The printed bill never shows a payment-method line at all (`generateBillBuffer`/`billTextLines` — removed after a reprint-after-settle showed a stale method from an earlier double-settled attempt); the Grand Total divider is the last line either generator prints.
- `POST /api/orders/:id/payment` guards against double-settlement with a conditional `WHERE paymentStatus='pending'` update (`storage.settleOrderIfUnpaid`). If that guard blocks a second request (double-tap, retried timeout), the response is now `409 { alreadySettled: true, order }` with a message naming the already-recorded method — previously this silently returned `200` with the stale pre-existing order, which looked like success while discarding whatever the second request tried to record. `POS.tsx`'s `settleMutation.onError` unwraps the JSON body out of `apiRequest`'s `"{status}: {rawText}"` error message to show the real reason.
- `SettlementDialog.tsx` has only **Cash and UPI** (Card removed — not used by this restaurant). Amount auto-fill is keyed off **UPI's own `onFocus`** (`handleUpiFocus`): if UPI is still 0, it fills with `grandTotal - cash` (the whole bill if cash is untouched, the remainder if cash was typed first). This used to be an `onBlur` cascade on *every* field that pushed the remaining balance into the next empty method (cash→upi→card) — since blur fires on losing focus for *any* reason, clicking the unrelated "Pay Later" checkbox (or anything else on screen) blurred whatever field was last focused and silently dropped an amount into UPI/Card. Ticking **Pay Later** now also resets cash/upi to 0 (`handleDueToggle`) and disables the payment table — `POST /api/orders/:id/payment` sets `paymentStatus` purely off `isDue` but still persists whatever `paidAmount`/`paymentBreakdown` came through, so a stale auto-filled amount riding along with `isDue:true` would have recorded a phantom "already paid" total on what's supposed to be an unpaid tab entry. `handleSettle` also force-sends an empty breakdown (`payments:[], totalPaid:0`) whenever `isDue` is true, as a second guard independent of the reset. There is no partial-pay-then-rest-due split — `isDue` is all-or-nothing at the server, so the dialog treats it the same way.

**Plain "Bill" button syncs the cart before printing.** `/api/print/bill` (`printRoutes.ts`) builds the ticket strictly from `order_items` in the DB — it has no knowledge of the browser's in-memory cart. `handleKOT`/`handleSaveAndPrint` already synced first (via `triggerSubmit` → `PUT /api/orders/:id/items`) before printing, but the plain "Bill" button (`handleBillPrint`, table/pickup POS only — Section mode's Bill already used `handleSaveAndPrint`) used to call `triggerBillPrint` directly with no save step. Real bug this caused: KOT-print 4 cart items → add a 5th (e.g. Mineral Water) with no further KOT/Save → hit "Bill" → the 5th item was visibly in the on-screen cart/total but silently missing from the printed bill, since the DB still only had the first 4. Fixed: `handleBillPrint` now sets `submitModeRef.current = "bill-print"` and calls `triggerSubmit()` first; `updateOrderMutation`'s `"bill-print"` branch calls `triggerBillPrint` (and fires `bill-requested`) only after the save succeeds — same sync-then-print shape as `save-print`, but stays on screen (no cart clear / navigate-away), since plain Bill is a mid-service reprint action, not a "finish and leave" one.

**Two independent "print bill" code paths — keep both in sync.** `POS.tsx`'s cart-panel Bill button goes through `handleBillPrint` → `triggerSubmit` → `triggerBillPrint` (above). The Tables-page card's print icon (`Tables.tsx`'s `printTableBill`) is a separate, simpler path straight to `printGateway.ts`'s `printBillDirect(orderId)` — it has no cart to sync (the Tables page never loads order items into a POS cart), so it just re-prints whatever's already persisted. It used to skip the `POST /api/orders/:id/bill-requested` status flip entirely, so printing from a running table's card never moved the table into `status:"billed"` — the card stayed "running" with the print button still showing, instead of flipping to the "Bill printed" label like the POS cart's Bill button produces. Fixed: `printTableBill` now fires `bill-requested` (+ invalidates `/api/tables`) on `"hardware"` and `"dispatched"` outcomes, matching the POS cart button's behavior; `"browser"`/`"noop"` (nothing actually got sent) intentionally don't flip status.

**"No new items added since last KOT" toast after a Bill print is about a *different*, optional auto-print — not the bill.** `POS.tsx`'s `triggerBillPrint` (used only by the POS-screen Bill button, not `printTableBill` above) has a `printSettings.kot.printOnBill` setting: when on, printing a bill *also* fires a follow-up `triggerKOTPrint` immediately after, so the kitchen gets a ticket for anything not yet sent. `triggerKOTPrint` asks `/api/print/kot` for the delta since the last KOT; if there's nothing new (the common case — the kitchen ticket usually already went out earlier), the server returns `reason:"no_delta"`, `handlePrintResponse` maps that to `outcome:"skipped"`, and the toast fires: **"Nothing new to print — No new items added since last KOT."** The bill itself already printed/dispatched fine (a separate `"Bill sent to printer!"` toast fires first, at `triggerBillPrint`'s outcome check) — this second toast is purely reporting that the *piggybacked KOT* had nothing to do, and can visually read as if the bill failed since it lands right after. Turn off `printOnBill` (Admin → Print Settings → KOT Print) if this piggybacked ticket isn't wanted.

**Phone (Vercel) → desktop thermal printer bridge.** Any request that can't print directly (Vercel, or any deployment with a `type: "usb"` printer) gets a `print_jobs` DB row (`shared/schema.ts`) plus a `PRINT_JOB` realtime broadcast (`publishRealtime`, same Pusher channel as `NEW_ORDER`/`KOT_UPDATE`) in addition to the `printJob` in the HTTP response — so a phone on the Vercel UI can trigger a print on the thermal printer wired to the desktop Electron host, which is also a Pusher subscriber. `POST /api/print/jobs/:id/claim` is an atomic `pending→claimed` update (a claim older than 2 min is reclaimable — `claimedAt` column) gating **both** consumers — the requesting tab's own `printGateway.ts` path (if it happens to be the Electron host) and the broadcast listener `client/src/hooks/usePrintJobBridge.ts` (mounted once in `App.tsx`, no-ops outside `window.electronAPI?.isElectron`) — so a job is never printed twice. `GET /api/print/jobs/pending` is a catch-up poll (mount + realtime reconnect only) for when the desktop host was offline at broadcast time; it is **not** the hot path — normal latency is ~1-2s end-to-end via the live push. The Electron `PrintQueue` (`desktop/print/printQueue.ts`) already auto-acks (`/api/print/ack`, now passes `jobId` too) after a successful print — **never ack a second time** from `printGateway.ts` or `usePrintJobBridge.ts`. On permanent failure it calls `POST /api/print/jobs/:id/release` to return the job to `pending` immediately rather than waiting out the stale-claim window. See `docs/ELECTRON.md`'s "Print flow (Vercel)" section for the full sequence.

**Multi-station printing (category routing + quick-POS sections).** Layered on top of the bridge above, additive and no-op when unconfigured. `KOTPrintSettings.categoryPrinterOverrides` (categoryId → printerId, Admin → Print Settings → KOT Print → "Category Routing") lets `/api/print/kot` split one tap's delta into **one ESC/POS ticket per routed printer** (same KOT number on each) — e.g. South Indian categories print on a separate counter printer while everything else keeps going to the main kitchen printer. Because one tap can now produce multiple tickets acked independently, `kotPrintCount`/`lastKotSnapshot` commit **once at dispatch**, not per-ack — `/api/print/ack` with a `jobId` only flips that `print_jobs` row to `printed`; it no longer double-touches order state. The Electron `printQueue.ts` dedup keys on **`orderId + ackType + printerId`** (not just order+type) for the same reason — a single host that owns several routed printers enqueues one ticket *per printer* for one order, and an order+type-only dedup silently dropped the second printer's ticket (real bug: a mixed South-Indian/Chinese order lost the South-Indian KOT when one PC claimed both jobs). `/api/print/bill` resolves a per-order bill printer the same way via `posSections[].billPrinterId` when every item in the order belongs to one section. A station (Electron host, or a browser tab in "print station" mode) can be scoped to specific printers via `printStationCore.ts`'s `localStorage` `ownedPrinterIds` (empty = owns everything, today's default) — both `usePrintJobBridge.ts` and the new `client/src/pages/PrintStation.tsx` (route `/print-station`) filter `PRINT_JOB` broadcasts and the `?printerId=` pending-poll by this. `PrintStation.tsx` is for devices with no Electron host (e.g. an Android tablet at an outdoor counter): it hands ESC/POS payloads to the **RawBT** app over a `rawbt:`/`intent://` URI and acks on handoff (RawBT has no success callback — the page's job list lets staff manually retap). `posSections` (`{id, name, categoryIds, billPrinterId}`, same Print Settings tab) also drives a dedicated card on the Tables page that opens `/pos?section=<id>` — `POS.tsx`'s `isSectionMode` filters the menu to the section's categories, hides the table workflow, and promotes a single "Print Bill" → Settle flow (`triggerSubmit`'s `save-print` mode stays on-screen with `activeOrderId` set instead of navigating away, so Settle can follow the same print). See `docs/ELECTRON.md`'s "Multi-station printing" section for the full design.

**Electron host must not claim a printer it can't execute.** `ownedPrinterIds` defaults to "owns everything" until a station explicitly narrows it — and the *only* UI that ever writes that key is the printer checklist on `/print-station` (reachable from the Electron window too, via the blue "Print Station — choose which printers THIS device prints" button in `PrinterSetupTab`, `PrintSettingsPanel.tsx`). Until that checklist is set, an open Electron host races the phone/RawBT station for every `PRINT_JOB` broadcast — including jobs for a phone-routed printer (registered `type:"usb"` with blank `windowsQueueName`/`vendorId`/`productId` by convention, so the server dispatches it remotely instead of executing it directly). If Electron wins that race it fails deterministically in `desktop/print/usbSend.ts` ("no Windows queue name configured"), burns 3 retries (~17s) in `printQueue.ts`, then releases the job — usually well after the phone's own claim attempt on the same broadcast already lost. Fixed at the code level too (belt-and-suspenders, doesn't rely on the checklist being set): `canExecuteLocally()` in `printStationCore.ts` checks whether a printer is actually locally executable (`usb` needs `windowsQueueName` or vendor/product id; `network` needs `ip`) and both `usePrintJobBridge.ts` and the Electron branch of `printGateway.ts` skip claiming when it isn't — reading printer configs from the already-cached `["/api/settings"]` query (`useQuery` in the hook, `queryClient.getQueryData` in the plain-function gateway) so there's no extra fetch per job.

**Two Electron hosts (e.g. a personal machine + the actual restaurant PC) can steal each other's jobs too — `windowsQueueName` is per-device data stored in a per-restaurant shared row.** `PrinterConfig` (incl. `windowsQueueName`) lives in the single shared `restaurant_settings.settings` blob (`server/settingsStore.ts`) — every Electron install reads the *identical* config, but a Windows print queue name is only ever valid on the one machine it was installed on. If a second desktop install of the app is left open (e.g. a dev/personal machine with no printer wired up) and its `ownedPrinterIds` is still the default "owns everything", `canExecuteLocally()`'s shape check alone can't tell the two installs apart — the wrong machine's config *looks* just as executable (same non-blank `windowsQueueName` string) even though the real printer isn't there. `desktop/print/usbSend.ts`'s fast path (`savedQueue` truthy) trusts that string blindly and calls `WritePrinter` directly with **no live verification** — if a Windows queue with that *exact same name* also happens to exist on the wrong machine (plausible: identical printer model set up there at some point, or the field was last saved *from* the wrong machine via "Detect Installed Printers"), `WritePrinter` succeeds (Windows accepts the raw bytes into a real local spooler queue) even though there's no physical printer behind it — the job shows "printed" everywhere in the app while the jobs pile up in that OS-level queue with **"Unknown status"** on the wrong PC, and the restaurant's real printer never receives them.

Mitigated (not fully closed — see limitation below) by `canExecuteLocallyVerified()` in `printStationCore.ts`: for a `usb` printer with a saved `windowsQueueName`, on a `win32` host (`window.electronAPI.platform`, exposed from preload's `process.platform` — **the check is skipped on Mac/Linux**, falling back to the `vendorId`/`productId` shape check instead, since `windowsQueueName` means nothing off Windows and `usbSend.ts`'s non-win32 branch prints via `libusb` using vendor/product id regardless of it; an earlier version of this fix wrongly applied the Windows-only check unconditionally and broke Mac/Linux hosts) it calls the `checkPrinterQueueExists` IPC (`desktop/main.ts`, reuses `shared/print/windowsPrinters.ts`'s `windowsPrinterQueueExists` — the same live `Get-Printer` check `runStartupHealthCheck` already used, now invoked reactively before every claim, not just at startup) to confirm a queue by that name is *registered* on *this* machine right now. Only a confirmed `true` is cached (`queueExistsTrueAt`, 30s TTL) — a `false` is **never** cached, because `usePrintJobBridge.ts`'s broadcast handler evaluates a given job's claim gate exactly once with no automatic retry, so a stale cached `false` could otherwise starve one specific job of any claim attempt for the rest of the session (only a later mount/reconnect catch-up poll would rescue it) rather than merely delaying it ~30s. Concurrent callers checking the same queue name (the tab's own `printGateway.ts` request path and `usePrintJobBridge.ts`'s broadcast listener both often fire for the same job) share one in-flight IPC round-trip (`queueExistsInFlight`) instead of spawning duplicate PowerShell processes. `printGateway.ts`'s multi-job loop (category routing can produce several routed jobs from one tap) runs all of a tap's `canExecuteHere` checks concurrently via `Promise.all` rather than one-at-a-time, so N routed printers don't serialize N PowerShell round-trips before any of them print.

**Structural limitation (by design, not a bug to chase):** `Get-Printer -Name` only proves a queue *name* is registered — it can't tell a real, connected printer apart from an orphaned/ghost queue installed under the same name with no hardware behind it. If the two machines coincidentally have a genuinely-registered queue under the identical literal name (exactly what produces the "Unknown status" symptom above), this check passes on both and can't disambiguate them. The durable fix is still `ownedPrinterIds` (a genuinely per-device, human-configured decision) plus always running "Detect Installed Printers → Save" from the physical machine each printer is actually wired to, never from a second/dev install pointed at the same shared DB.

**On-screen reminders for the "page is open but not actually listening" trap.** Since the Station Mode toggle being off is invisible from a glance at the page (it just looks like the normal UI), `/print-station` now shows a persistent red banner when `enabled` is false. And since navigating away from `/print-station` to place an order (Issue A/B's "same phone, two jobs" trap) silently stops all listening with zero indication anywhere else in the app, `PrintStationStatusBadge` (`client/src/components/PrintStationStatusBadge.tsx`, mounted once in `App.tsx` next to `UpdateNotification`) shows a floating "Print Station idle — tap to resume" pill on every OTHER route (including POS, which has no `TopNav`) whenever this device's `printStation.enabled` flag is on — reading/writing that flag now goes through `isStationEnabled()`/`setStationEnabled()` in `printStationCore.ts` (previously a private constant duplicated only in `PrintStation.tsx`).

**`/print-station`'s "Station mode" toggle gates everything, independent of the page being open.** All of `PrintStation.tsx`'s listening logic (`PRINT_JOB` broadcast handler, mount/reconnect catch-up poll, even the wake-lock) starts with `if (!enabled || isElectron) return;` — `enabled` is a separate ON/OFF switch (`localStorage["printStation.enabled"]`), not implied by the page being visible. A phone can have `/print-station` open and still print nothing if that switch was never flipped on. Also: a single phone used both to place orders (e.g. `/pos?section=<id>`) and to run the print station only listens while the **`/print-station` route itself** is the active page — the ordering page runs none of this code, so a job dispatched while that phone is mid-order sits `pending` until the phone actually navigates to `/print-station` (whose mount-time catch-up poll then rescues it). A dedicated second device (or a second always-open tab) for the print-station role avoids this.

**Section orders vs. generic pickup (`orders.posSectionId`).** A quick-POS order is stamped with its section id at creation (`posSectionId` on `orders` — nullable text; `POST /api/orders` passes any real column through, no server change needed). This is the ONLY thing distinguishing a section counter order from a normal pickup (both are `orderType:"takeaway"`, no `tableId`) — don't infer section-ness from items. `useLiveOrders.ts` excludes tagged orders from the generic 📦 pickup/🛵 delivery edge rail (`LiveOrdersPanel.tsx`); they surface in a tap-only **flyout floating in front of the section card** (`SectionOrdersFlyout.tsx`, reuses the exported `OrderRailCard` with a `posUrl` override), and tapping a row reopens `/pos?orderId=<id>&section=<id>` (the simple section POS). Flyout interaction: the amber count badge is the **only** way to open it and is **open-only, never a toggle** — touch devices emulate `mouseenter` before `click`, so a toggle would open-then-close on one tap; closing is tap-away (`pointerdown` outside). Desktop hover-to-open (with an 80ms leave-grace) was removed by request — it was unwanted, purely a badge tap now. The rail also now drops `status="served"` orders **immediately** (previously they lingered until midnight with a grey chip — confused the owner). Bill routing prefers `order.posSectionId` → section `billPrinterId`, falling back to the all-items-in-section-categories inference for legacy orders. Settle-freeze guard: every path that sets `settlePhase="processing"` has a matching `setSettlePhase("idle")` in its error/early-return branch (`createOrderMutation.onError`, `updateOrderMutation.onError`, `onSubmit` empty-cart return) — a failed settle must never leave the Settle/Print buttons stuck at "…".

**Section POS is a stripped-down counter mode** (built because outdoor-counter staff verbally quoted bills without tax/container — the true total must be the thing they read out). In `isSectionMode`, POS.tsx hides: RoleSwitcher, + New Order, search + short-code, the desktop right cluster ("Adding as" strip + customer name/phone), the mobile customer strip and "Adding as" strip, the Discount row, the cart column headers, and the by-serviceMode cart grouping (flat list). Kept: Back, amber section badge, category pills, Clear all, mobile Menu/Cart tabs; `SettlementDialog` stays outside all section conditionals. Section-only components live in `client/src/components/section-pos/`: `SectionParcelToggle` (big "Eating Here"/"Parcel · +₹N/item" segmented strip under the top bar, "New items go to" eyebrow) and `SectionActionBar` (compact Items/GST/Container breakdown + h-16 "Print Bill · ₹grandTotal" + Settle; handlers are the existing `go(...)` PIN-gated ones, `settleLabel` ternary computed in POS.tsx — no new `settlePhase` writers). **Parcel is per-item, same backend logic as tables** (the owner's counter takes mixed orders — eat 2 dosas here, parcel 1 idli): the big toggle just drives `activeItemMode` (`pickup` = parcel, `dinein` = eating here) so NEW items inherit it; each item keeps its own `serviceMode`, the existing per-item container computation and server `PUT /items` recompute apply unchanged, and the section cart reuses the table grouping with counter labels (🍽 Eating Here / 🥡 Parcel; delivery also renders as Parcel). Per-row "Make Parcel"/"Make Eating Here" (`flipItemMode`) flips one line, rewriting its mode-embedded cartKey and merging if the target key already exists. Reopen rehydration points the toggle at the LAST saved item's mode. Menu tiles/cart rows/billing panel get bigger touch-target classes behind `isSectionMode` conditionals only — normal POS strings untouched.

**Reports page date picker: no exit animation on the dropdown panel — this is deliberate.** `Reports.tsx`'s `DateRangePicker` used to close via `AnimatePresence` + a 150ms `exit` transition. Picking a preset calls `onChange(range)` (parent `dateRange` state → every `key={`sales-${dateRange.start}-${dateRange.end}`}`-keyed chart section below remounts) and `setOpen(false)` in the same handler — React batches these, but `AnimatePresence` still keeps the panel mounted and animating out for that 150ms *after* the batch commits, so the still-visible, `position:absolute` panel and the data-driven reflow happening underneath it were racing. Real bug this caused: picking **Today** specifically (near-empty data, so the remounting chart/cards collapse to a much shorter height than whatever was showing before) made the closing panel visibly jump/displace during its exit animation — other presets rarely showed it because their content heights were closer to each other. Fixed by dropping the exit animation (plain `{open && (...)}` instead of `AnimatePresence` + `exit`) so the panel unmounts in the same render as the data change, before any reflow can happen underneath it. Don't re-add an exit transition here without also decoupling the panel from the reflowing content (e.g. a portal), or this comes back. The nested `showCustom` sub-panel inside it keeps its own `AnimatePresence` — that one's fine, it's a pure local UI toggle with no data refetch tied to it.

## Order History & Billing (per-day view)

Both pages default to showing only the **current business day**'s orders — previously they fetched the entire unscoped order history every load, which also just kept growing over time.

- **Business day, not calendar day** (`shared/businessDay.ts`): a restaurant open past midnight means a strict `00:00–23:59` filter would go empty mid-shift the instant the clock ticks to 12:00 AM. A business day instead runs **5:00 AM IST → 4:59:59.999 AM IST the next day** (`BUSINESS_DAY_CUTOFF_HOUR`, currently a fixed constant, not an admin setting). `businessDateOf(date)` resolves any timestamp to the business day it belongs to; `businessDayRange(dateStr)` returns the exact UTC instant bounds for that day. Built the same way `formatISTDateTime` is — `Intl.DateTimeFormat` pinned to `Asia/Kolkata` — so it's correct regardless of the server/browser's ambient timezone.
- **`shared/businessDay.ts` also exports plain IST-calendar helpers** (`istHour`, `istCalendarDate`, `istMonthDay`, `istCalendarDayRange`) for call sites that want the real IST wall-clock hour/date, not the 5am-cutoff business day — WhatsApp quiet-hours gating, "already messaged this customer today" dedup (resets at IST midnight), birthday-field matching, and the daily scheduler's once-per-day job gates. **A large, systemic sweep found this exact bug (raw `new Date().getHours()`/`.getDate()`/`.toISOString().slice(0,10)`/`.toDateString()` reading the SERVER's ambient timezone instead of IST) in over a dozen places**, all now fixed to use these helpers: `server/services/dailyScheduler.ts` (its `today`/`hour` gate — `today` was UTC via `toISOString()` while `hour` was server-local, so they could disagree and a job could fire twice for the same real IST day); `server/services/dailyDigestService.ts` (`buildDailyMetrics`'s day-range AND its `digestDate` dedup key — local-midnight `start` serialized via UTC `toISOString()` meant the dedup lookup could find *yesterday's* already-sent digest and silently overwrite it with today's data; also its hourly-peaks bucketing); `server/services/birthdayService.ts` (both `todayMonthDay()` and its own separate `alreadySentToday` dedup); `server/services/crm/automationRuleEngine.ts` (`hasJobToday`/the settlement-dedup `recentJob` check, **and** a second, independent BIRTHDAY-trigger date match in `evaluateRule`); `server/services/aiMessageService.ts` (`isGoodSendTime`'s 11PM–7AM quiet-hours guard — got the wrong 8-hour window entirely on a non-IST host, both blocking legitimate daytime sends and allowing genuine late-night-IST sends, the ban-avoidance risk this guard exists to prevent); `server/services/whatsapp/outboundQueue.ts` (`enqueueWhatsApp`'s same-day dedup — which **also** checked the wrong column, `scheduledAt` instead of `executedAt`, so a job enqueued one day but deferred to actually send the next still looked "sent today" by its stale scheduled time, letting a real duplicate through; and `sentToday()`'s `maxPerDay` counter); `server/services/automationStore.ts` (`hasBeenMessagedToday`'s file-log dedup, via `toDateString()`); `server/services/customerAutomationService.ts` + `client/src/hooks/useCustomerIntelligence.ts` (both compute a customer's "peak order hour" — now IST on both sides, matching each other and the `isGoodSendTime` check they feed). Also fixed: `storage.getSoldToday`/`getDashboardStats`/`getSalesChart`/`getCategorySales`/`getDashboardTopItems` and `routes.ts`'s `/api/live-status`, `/api/reports/payment-summary`, `/api/reports/weekly`, `/api/reports/staff-tables` (previously pinned **UTC**, not IST — a real timezone, but not the restaurant's), `/api/reports/sales` — all used a naive local-midnight (or UTC) "today," which disagreed with Order History/Billing's already-correct business-day filtering for any order placed between midnight and 5am IST, **even on a server actually hosted in IST** (business day ≠ calendar day by construction, so this wasn't just a "wrong server timezone" bug). `getSalesChart`/`/api/reports/weekly`'s per-day chart bucketing was fixed the same way (`businessDateOf`/`shiftBusinessDate` instead of raw UTC `toISOString()` date keys). Regression-locked by `scripts/verify-ist-datemath.ts` (in `test:pure`).
- **`DayPicker`** (`client/src/components/DayPicker.tsx`): shared single-day picker — "Today" by default, ◀/▶ day-shift buttons, and a native date input to jump anywhere (max = today, since business data is history-only, not future). Used by both `Orders.tsx` (Order History) and `Billing.tsx`.
- Both pages pass the picked day's `businessDayRange()` bounds as `startDate`/`endDate` (full ISO instants, not date-only strings) to the existing `GET /api/orders?startDate=&endDate=` — no new endpoint needed, just a client-side query change (custom `queryFn`, mirroring the pattern `Reports.tsx`'s own date-ranged queries already use, rather than the default `queryKey.join("/")` fetcher which can't carry query-string params).
- **Server-side additive change**: `GET /api/orders` (`routes.ts`) used to require *both* `startDate` and `endDate` together (else it fell through to `status`-only or unfiltered). `storage.getOrdersByDateRange` now takes **either bound optionally** (`gte`/`lte` conditions built conditionally) — `endDate` alone means "everything up to X", used by Billing's backlog count below. `status` also now combines with a date range (post-filtered in JS) instead of being mutually exclusive with it.
- **Billing's unpaid-backlog banner**: since Billing's list is billable orders (`pending|preparing|ready|served`) that may still be unpaid, scoping it to "today" by default risks silently hiding an old unsettled order. A banner ("N unpaid orders from before today") appears whenever such a backlog exists for the *current* day view (`isToday && !showAllPending`), computed via a lightweight `endDate`-only query (everything before today's business-day start) filtered client-side for `paymentStatus !== "paid"`. Its "Show all" link flips `showAllPending`, which reverts to the original unscoped fetch; picking any date via `DayPicker` clears that flag again. This is separate from the all-time Dues/Pay-Later report (`GET /api/reports/tabs`) — this banner is just a heads-up on the Billing page itself, not a replacement for that report.

## Staff, Attendance & Payroll

Two identity systems (see `docs/superpowers/specs/2026-05-21-unified-role-user-management-design.md`), **both created in Admin → Accounts**:
- **`users`** (`username/password`, roles admin/manager/staff) — login + POS permissions. HR fields live in `staffProfiles` (`designation`, `biometricId`, `monthlySalary`).
- **`staffMembers`** — PIN name-card mobile login **and** attendance-only staff. Carries `designation`, `biometricId`, `monthlySalary`, `excludeFromPayroll`. **PIN is optional** — a `pin == null` member is *attendance-only* and never appears as a login card (clocks in by fingerprint).

**Mobile name-card login** (`showOnMobile` boolean on **both** `users` (default false) + `staffMembers` (default true)):
- Public `GET /api/staff-members` returns **unified login cards** — staff members **and** non-admin accounts that have `showOnMobile` ON + a PIN, each tagged `kind:"staff"|"user"`. Admins/owner are never card-eligible.
- `POST /api/auth/card-login {kind,id,pin}` logs in either a staff member (staff-tier session) or an account (its real role); admins blocked. `Login.tsx` calls it with the card's `kind`.
- Admin → Accounts shows a **Mobile Card on/off `Switch`** per row (`toggleUserCard`/`toggleStaffCard` → `PUT /api/users/:id`|`/api/staff-members/:id {showOnMobile}`); disabled for admins and for anyone without a PIN. Smoke test: `scripts/verify-mobile-card.ts`.

**⚠️ Id-collision gotcha:** `users` and `staffMembers` share the integer id space, and a staff-member session is `{ id: sm.id, _isStaffMember: true }`. Any "self" endpoint that keys on `req.user.id` MUST disambiguate by `_isStaffMember` (→ `staffMemberId` vs `userId`) or it's a cross-table IDOR. Already guarded: `/api/attendance/me`, `/api/payroll/me/:month`, and (via `server/selfScope.ts`'s `requireUserAccount` middleware) `PUT /api/auth/profile` + `PUT /api/auth/password`. Same rule applies to any write that stamps `req.user.id` onto a shared table: `orders.createdBy` (`users.id`) and `orders.createdByStaffMemberId` (`staffMembers.id`, `scripts/migrate-order-creator.mjs`) are separate nullable columns for exactly this reason — `POST /api/orders` (`routes.ts`) picks one based on `actor._isStaffMember`, never stamps the raw id into `createdBy` alone. `GET /api/staff/performance` (Staff page → Sales tab, `staffRoutes.ts`) resolves names against a union of both tables (like `getPayrollPeople()`) and excludes admin/owner by construction; unresolved/deleted-creator rows merge into one "Unassigned" bucket rather than silently misattributing to a same-id row in the other table.

**Fixed real-world instance (was live, now closed):** `PUT /api/auth/profile` used to call `storage.updateUser(Number(currentUser.id), …)` with no `_isStaffMember` check and returned the updated row stripped of only `password` — so a staff-tier PIN session whose `sm.id` collided with a `users` row could rename that account **and receive its plaintext `pin`/`totpSecret` back in the response** (both columns existed but weren't in the strip list). That leaked PIN, replayed into `POST /api/auth/verify-pin`, granted a real `requireElevation("manager")` session grant — a full privilege-escalation chain from a bare staff PIN. Any new "self" endpoint MUST use `requireUserAccount` (403s a staff-member session before the handler runs) and `sanitizeUser()` (strips `password`/`pin`/`totpSecret` from any `users`-shaped response) from `server/selfScope.ts` — don't hand-roll the destructure again. Regression-locked by `scripts/verify-self-scope.ts` (in `test:pure`).

**Authorization:** payroll/roster reads expose salaries → gated by **`requireManagerOrAdmin`** (`/api/payroll/people`, `/api/payroll/report/:month`) so staff-tier (PIN) sessions can't read them; managers keep Staff-page access. Admin-only config (`GET/POST /api/settings/staff-page-access` + `apply-role`) is `requireAdmin`. Self-service `/api/*/me` stays `requireAuth`.

**Payroll + biometric run on a UNION of both** (`storage.getPayrollPeople()`):
- `users` with role ∈ {manager, staff} (admins/owner excluded) via `staffProfiles`, **plus** `staffMembers` (skip `excludeFromPayroll`). Each person is `{ kind:'user'|'staff', id, name, role, biometricId, monthlySalary }`.
- `attendance` rows key on **either** `userId` **or** `staffMemberId` (`userId` nullable; `upsertAttendanceForStaffMember` mirrors the user version; `getAttendance({ staffMemberId })` + `displayName` resolve either).
- `deviceAttendanceService.ts` maps `biometricId → staffMemberId` (primary) then `→ userId` (fallback) and writes via the matching path.
- `getPayrollReport(month)` computes over `getPayrollPeople()`; rows carry `kind`, `userId?`, `staffMemberId?`, `name`, `designation` (+ `username`/`role` aliases for the table UI). Owner/admins absent by construction (shown as an **"Owner"** badge in Admin).
- The Staff page **Attendance/Summary** tabs read the device `attendance` table over the roster:
  `getAttendanceRange({from,to,key?})` (`GET /api/attendance/range`, fields mirror the old UI:
  `employeeName/punchIn/punchOut/hoursWorked`) and `getAttendanceSummary({from,to})`
  (`GET /api/attendance/summary`). The **Google-Sheet importer is gone** (staffRoutes gsheet endpoints +
  `attendanceService.ts` deleted; `attendanceRecords` table left dormant). The **Today** board + EMPLOYEE
  filter use `GET /api/payroll/people`. **Shifts** and **Leaves** are both union-based now (see "Shifts &
  auto-detection" and the leaves note below — the old manager/staff-users-only `/api/staff/accounts`
  endpoint they used is gone). Biometric/salary **`StaffBiometricSetup`** lives in the **Device** tab now
  (not Payroll). Smoke test: `scripts/verify-attendance-tabs.ts`.

### Shifts & auto-detection (Staff → Shifts tab)
The Weekly Roster shows **actual worked shifts auto-detected from biometric punches**, alongside optional manual assignment. Key pieces:
- **`shift_assignments`** (`shared/schema.ts`) is the source of truth for *which shifts + their hours*. `userId` is now **nullable** with a parallel **`staffMemberId`** (exactly one set — same dual-key pattern as `attendance`), plus `source` (`'manual'|'auto'`), `clockIn`, `clockOut`, `workingHours`. **Multiple rows per person/date are allowed** (Morning + Evening on one day). Migration: `scripts/migrate-shift-detection.mjs`.
- **`getRoster`** (`storage.ts`) builds people from **`getPayrollPeople()`** (union of `users` manager/staff + `staffMembers`, owner/admin excluded) — this fixed the bug where only login accounts appeared. It returns `assignments[date]` as an **array** of `{assignmentId, shift, source, clockIn, clockOut, workingHours}`. `POST /api/shifts/roster` takes `{kind,id,date,shiftId}` and inserts a `source:'manual'` row; `deleteShiftAssignment` only removes **manual** rows (auto re-derive from punches).
- **Auto-detection** lives in `deviceAttendanceService.ts` via `shared/shiftTime.ts` (`shiftWindow` with **midnight-wrap**, `matchShift`, `detectSessions`). On each punch batch it pools this batch's times **+ the in/out of existing `source:'auto'` sessions** (each auto row keeps BOTH endpoints, so interior shift boundaries survive across sync batches — the single `attendance` row only keeps global first/last), sorts, pairs sequentially `[in,out]…`, matches each pair to a shift window, and rewrites the person/date auto rows via `storage.replaceAutoShiftSessions` (manual rows untouched). The `attendance` day row stays one-per-day but its `workingHours` = **Σ session spans** (excludes midday gaps), `status` half-day if <4h.
- **Midnight-crossing shifts** (e.g. Evening 16:00–00:00) compute correctly now: `durationHours` is computed **server-side** in `storage.createShift`/`updateShift` via `shiftWindow(...).hours` (wraps `end += 24h` when `end<=start`) — the old client-only `Math.max(0, end-start)` clamped it to 0.00h. Don't trust a client-sent `durationHours`.
- **`POST /api/attendance/recompute-shifts`** (`requireAdmin`, "Recompute" button on the Shifts tab) backfills a month via `recomputeShiftSessions`. **Limitation:** days that collapsed to a single first→last span *before* this feature lost their interior punches, so they can only resolve to one session — going forward, live punches split correctly.

### Leaves (Staff → Leaves tab)
Same union fix as Shifts: `leaves.userId` is now **nullable** with a parallel **`staffMemberId`** (`scripts/migrate-leaves-staffmember.mjs`) — before this, PIN/biometric-only staff members couldn't appear in or apply for leave at all (`getLeaves` joined `users` only). The "Apply Leave" dropdown now sources from **`GET /api/payroll/people`** (not the legacy `/api/staff/accounts`), encoding the selection as `"user:<id>"` / `"staff:<id>"` since ids collide across the two tables. `POST /api/leaves` takes `{kind,id,...}` and stamps exactly one of `userId`/`staffMemberId`; `getLeaves` resolves against both tables and returns a unified `displayName` (mirrors `getAttendance`'s `AttendanceWho` pattern) — the leave list renders `leaf.displayName`, not `leaf.user?.username`.

**Leaves/Shifts writes are `requireManagerOrAdmin`, not `requireAuth`.** `POST /api/leaves` takes an arbitrary `{kind,id}` target (not "self"), and `PUT /api/leaves/:id` is the approve/reject action with no self-approval guard — a bare staff-tier PIN session could previously file a leave request as anyone, or approve/reject any leave including its own. `POST/PUT /api/shifts` (shift-type definitions) and `POST /api/shifts/roster` + `DELETE /api/shifts/roster/:id` (assigning/unassigning any employee to any date) are the same class of issue — roster management, not self-service. `Staff.tsx` (the only client of any of these) has **no client-side role check anywhere in the file**, so a staff-tier person only ever reaches this page at all via an explicit per-person `staffPageAccess` grant (`/staff` is not in any role's `ROLE_PAGE_DEFAULTS`) — if that grant exists for someone today, their "Apply Leave" button now 403s, a deliberate tradeoff: closing the confirmed approve-any-leave / edit-any-roster hole outweighs that narrow inconvenience. A scoped self-service "apply for my own leave" endpoint would be a genuine new feature to build later, not a gap to leave open now. The four `GET`s (`/api/leaves`, `/api/shifts`, `/api/shifts/roster`) stay `requireAuth` — reading isn't the vulnerability, and the page should still at least render for anyone who can see it.

**UI split (the user's chosen model):**
- **Admin → Accounts** = the *only* create/edit/delete place. The **Add Staff Member** dialog sets name + **Role** (`STAFF_ROLE_OPTIONS`: Service/Cook/Cleaning/Cashier/Other — Manager is the separate tier) + optional PIN; role → `designation` → payroll.
- **Staff page → "Staff & Biometric Setup"** = *annotate-only* list over `GET /api/payroll/people`: read-only **name** + read-only **role** + **Biometric ID** + **Salary** (`PersonRow`). Saves route by `kind` → `PUT /api/staff/:id/profile` (user) or `PUT /api/staff-members/:id` (staff). No add/delete/role-edit here. Payroll salary edit routes the same way.
- Smoke tests (no HTTP): `scripts/verify-staff-payroll.ts`, `scripts/verify-union-payroll.ts`.

## Deployment modes

The same app ships three ways. **Baileys (and the outbound worker + schedulers) only run inside a persistent process — never serverless.** The driver/worker start *only* in `server/index.ts`'s `server.listen` callback.

- **Vercel (web + API):** `vercel.json` → `api/index.ts` → `dist/app-bundle.js` (built from `server-fn.ts`). This is a stateless request handler — it does **not** call `server.listen`/`initWhatsAppDriver`/`startOutboundWorker`. So Vercel has **no Baileys, no inbound bot, no queue draining**. Meta Cloud API is stateless HTTPS + webhook in principle, so it's the one driver that *could* run here — but `server-fn.ts` didn't set up the `rawBody` capture `whatsappRoutes.ts`'s webhook HMAC check needs (present only in `server/index.ts`), so it 401'd unconditionally on every Meta webhook request on Vercel before that was fixed. `server-fn.ts` now mirrors `server/index.ts`'s `express.json({ verify })` rawBody stash, so Meta Cloud API is viable on Vercel as of this fix — still unverified end-to-end (needs a real signed webhook hitting a deployed preview).
- **Persistent process (`npm run dev`/`npm start` = `server/index.ts`):** full stack incl. Baileys. This is the only place auto-send works.
- **Electron host build (`pack:win:host`, flag `BAGICHA_EMBEDDED=1`):** `desktop/main.ts` spawns the bundled server (`dist/index.js`) as an `ELECTRON_RUN_AS_NODE` child with `BAGICHA_DATA_DIR=app.getPath("userData")` + baked `DATABASE_URL` (override via `userData/host-config.json`), waits for `/api/auth/context`, then loads the window from `http://localhost:5179` (renderer/WS auto-target localhost). Makes the admin desktop the always-on WhatsApp host **while the app is open**. Uses `asar:false` (so the child Node resolves `dist/index.js` + node_modules from disk). **Baileys is a singleton — only ONE host build per number.** Normal Electron builds (`pack:win`) stay thin clients → remote API. Windows-only (host build); the thin-client Electron app also ships for **macOS** via `pack:mac` (must run on macOS — the `release-mac` job in `.github/workflows/release.yml` builds x64+arm64 in CI and publishes to the same GitHub Release as Windows). **The `release-mac` job exists only on `Thermal-Printer`, not `main`** — a release tagged off `main` produces no Mac build at all.

### macOS signing (see `docs/MAC-SIGNING.md`)

No paid Apple Developer ID, so **two separate problems** that are easy to conflate:
- **Install:** a browser-downloaded dmg gets `com.apple.quarantine`; Gatekeeper finds no notarization ticket and reports **"damaged"** (Apple's modern phrasing on Apple Silicon — *not* the old bypassable "right-click → Open" prompt, which is what the workflow's stale header comment still claims). The flag is the entire cause: deliver via **USB** (FAT32/exFAT can't carry xattrs, so it's stripped in transit) and it installs clean, no Terminal. `xattr -cr` is the fallback.
- **Auto-update:** `electron-updater` → **Squirrel.Mac** validates an update's signature against the running app's designated requirement. **Ad-hoc signatures are hash-derived and differ every build, so they can never match** — macOS auto-update is impossible while ad-hoc signed, and no config in `electron-builder.yml`/`desktop/updater.ts` disables that check (it's Apple's framework). Windows is unaffected (NSIS updates unsigned apps fine) — the platforms are genuinely asymmetric.

Mitigation in progress: a **self-signed cert** (`mac.identity` in `electron-builder.yml`) gives a *stable* signature across builds → fixes auto-update only; USB delivery fixes install. `hardenedRuntime` is **false** deliberately — it only pays off with notarization and can block native modules (`usb`). **Unproven — validate per `docs/MAC-SIGNING.md` Phase 0 before relying on it.** Keep `mac.target`'s `zip` (electron-updater needs it + `latest-mac.yml`). If the cert is ever lost/changed/expired, auto-update silently dies and every Mac needs a manual reinstall.
